# AdoruWorld 筛选与搜索架构分析及重构方案

> 适用版本：2026-06-23  
> 背景：Archives.vue / Dex.vue / PostSearch.vue 三处各有一套筛选/搜索逻辑，模式不统一、代码重复、PostSearch 功能未完成。

---

## 一、现状全景图

### 1.1 三处实现的对比

| 维度 | Archives.vue | Dex.vue | PostSearch.vue |
|------|-------------|---------|---------------|
| **数据加载策略** | 一次性全量加载 (`getArchives()`) | 分批加载 (`getDexs({ limit: 12 })`) 带 loadMore | 每次 query 变化都调 `getPosts()` 重新请求 |
| **筛选执行层** | 纯客户端 computed | 混杂：Category/Status → 触发 API 重取；searchQuery → 客户端 computed | 纯服务端（通过 URL query 传给 API） |
| **筛选字段** | Category / Tag / 日期范围 | Category / Status / 搜索关键词 | Keyword / Category / Tag（但 keyword 未传参） |
| **搜索方式** | 无 | 客户端字符串 `.includes()` 匹配 | URL 驱动，但 `keyword` 参数未传递给 `getPosts()` |
| **空状态处理** | 隐藏空月份 | 有一条 "没有找到记录" | 有完整空状态 UI |
| **分页/加载更多** | 无（全量） | 有 loadMore（但 loadMore 不兼容客户端搜索） | 有 query-page 分页（但未实现翻页按钮） |
| **状态持久化** | 无（URL 无同步） | 无（刷新丢失） | 有（URL search params 驱动） |

### 1.2 核心痛点清单

```
□ [严重] 三套筛选模式零共享 —— 没有 composables、没有 utils、没有通用 FilterModel
□ [严重] Dex.vue 的场景分裂 —— 切分类/状态触发 API 重取（服务器筛选），但 searchQuery 是客户端筛选
   → 客户端搜到"3 条结果"后按"加载更多"，loadMore 从服务器拉新数据（不匹配 searchQuery）
   → searchQuery 只在已加载的 12/24/36 条里搜，不是全量搜索
□ [严重] PostSearch.keyword 断了 —— 路由传参有 keyword，但 API 调用时没传
   → `/posts?keyword=xxx` 接口可能也不存在
□ [中等] Archives 组件逻辑过重 —— 筛选、分组、日期分离三选都在一个 400+ 行组件里
□ [中等] 没有 URL 状态同步 —— Archive/Dex 的筛选状态刷新即丢失，不可分享
□ [轻微] Dex 的 watch 触发 API 重取时，searchQuery 会被清掉（搜索框内容还在但筛选结果重新开始）
```

## 二、问题深层分析

### 2.1 问题一：架构分层缺失

当前只有 `store` + `view` 两层，缺少中间的 **composable** 抽象层：

```
当前：   API (utils/request.ts)
          ↓
        Store (pinia)
          ↓
        View (vue) ←── 筛选/搜索/分组/排序 全部挤在组件内
```

应该有的：

```
        API (utils/request.ts)
          ↓
        Store (pinia) — 数据获取 & 缓存
          ↓
   ┌──── Composables ────┐    ←── 筛选逻辑、搜索逻辑、分页逻辑复用
   │ useSearch / useFilter │
   │ usePagination         │
   └────────┬─────────────┘
            ↓
        View (vue) — 只负责渲染
```

### 2.2 问题二：「服务端筛选 vs 客户端筛选」边界模糊

这是最根本的问题。当前的情况：

| 视图 | 期望 | 实际 |
|------|------|------|
| Archives | "在已加载的全部数据里快速筛选" | ✅ 实现正确（全量加载 + computed） |
| Dex | "在全部图鉴里按分类/状态/关键词筛选" | ❌ 割裂 —— 分类/状态走服务端，关键词走客户端 |
| PostSearch | "全局搜索全部文章" | ❌ 未完成 —— keyword 参数未落地 |

### 2.3 问题三：PostSearch 的设计定位未定

PostSearch 应该是什么？

- **A) 全局搜索入口** —— 搜索全部内容类型（文章 + 图鉴 + 媒体）  
  → 需要后端提供统一搜索接口（如 `GET /search?q=xxx&type=post,dex,media`）
- **B) 文章搜索页面** —— 专门搜索文章（含全文 content）  
  → 后端需要支持 `GET /posts?q=xxx&in=title,content,tags`
- **C) 仅作为路由驱动的文章列表筛选**  
  → 其实就是 /posts?category=xxx 的展示页，可以并入其他页面

当前代码倾向于 B 或 C，但 keyword 断了线。

## 三、重构目标

### 3.1 原则

1. **统一模式** —— 相同性质的功能用相同的方式实现
2. **服务端筛选 vs 客户端筛选，一个视图内不要混用**
3. **composable 复用** —— filter、search、pagination 提取为 composable
4. **URL 状态同步** —— 可分享、可刷新、可后退
5. **渐进式** —— 不要一次性大改，分阶段进行

### 3.2 决策矩阵

根据数据量和交互特点，为三个视图明确筛选执行层：

| 视图 | 数据总量预期 | 交互特点 | 推荐策略 |
|------|------------|---------|---------|
| Archives | ≤ 500 篇（无 content） | 高频切换分类/标签 | **客户端 computed** ✅ 保持现状，提取 composable |
| Dex | 可能 1000+ 条 | 按分类浏览（低频），按关键词搜索（低频） | **纯服务端**：所有筛选 → API 参数 |
| PostSearch | 全局 | 按关键词搜索（低频） | **纯服务端**：所有搜索条件 → API 参数 |

## 四、方案详细设计

### 4.1 基础设施：创建 composables 层

新建目录 `client/src/composables/`：

```
composables/
├── useClientFilter.ts      # 客户端筛选（小而稳的数据）
├── useServerSearch.ts      # 服务端搜索（大数据/全文）
├── usePagination.ts        # 分页/加载更多
├── useUrlFilterSync.ts     # URL query ↔ 筛选状态双向同步
├── useDebounce.ts          # 防抖工具
└── index.ts                # 统一导出
```

#### `useServerSearch.ts` — 服务端搜索

```typescript
// 适用场景：搜索条件需要发往服务器
// Dex.vue 和 PostSearch.vue 改造后用

import { ref, watch, type Ref } from 'vue'
import { useDebounce } from './useDebounce'

export interface SearchParams {
  keyword?: string
  category?: string
  tag?: string
  // 其他通用搜索参数
}

export function useServerSearch<T>(
  fetcher: (params: SearchParams) => Promise<T[]>,
  options?: { debounceMs?: number; initialParams?: SearchParams }
) {
  const params = ref<SearchParams>(options?.initialParams ?? {})
  const results = ref<T[]>([])
  const loading = ref(false)
  const debouncedParams = useDebounce(params, options?.debounceMs ?? 300)

  watch(debouncedParams, async (newParams) => {
    loading.value = true
    try {
      results.value = await fetcher(newParams)
    } finally {
      loading.value = false
    }
  }, { immediate: true })

  return { params, results, loading }
}
```

#### `useUrlFilterSync.ts` — URL 状态同步

```typescript
// 核心功能：将筛选状态双向绑定到 route.query
// Dex.vue 和 PostSearch.vue 应该支持

import { watch } from 'vue'
import { useRoute, useRouter } from 'vue-router'
import type { Ref } from 'vue'

export function useUrlFilterSync(filters: Record<string, Ref<any>>) {
  const route = useRoute()
  const router = useRouter()

  // 初始化：从 URL 读取
  onMounted(() => {
    for (const [key, ref] of Object.entries(filters)) {
      if (route.query[key] !== undefined) {
        ref.value = route.query[key]
      }
    }
  })

  // 同步：ref 变化 → 更新 URL
  // 注意：使用 replace 避免堆栈溢出，debounce 避免频繁写入
  // filters 变化 → URL.update (push/replace)
  // URL 变化（后退/前进）→ filters 回读
}
```

## 五、详细代码设计

### 5.1 useDebounce.ts

```typescript
import { ref, watch, type Ref } from 'vue'

export function useDebounce<T>(source: Ref<T>, delay: number = 300): Ref<T> {
  const debounced = ref(source.value) as Ref<T>
  let timer: ReturnType<typeof setTimeout> | null = null

  watch(source, (val) => {
    if (timer) clearTimeout(timer)
    timer = setTimeout(() => {
      debounced.value = val
    }, delay)
  })

  return debounced
}
```

### 5.2 useClientFilter.ts (草图)

```typescript
import { computed, ref, type Ref, type ComputedRef } from 'vue'

type FilterFn<T> = (item: T) => boolean

export function useClientFilter<T>(items: Ref<T[]> | ComputedRef<T[]>) {
  const filters = ref<Record<string, FilterFn<T>>>({})

  const setFilter = (key: string, fn: FilterFn<T> | null) => {
    if (fn) {
      filters.value[key] = fn
    } else {
      delete filters.value[key]
    }
    // 触发 reactivity
    filters.value = { ...filters.value }
  }

  const clearFilters = () => {
    filters.value = {}
  }

  const filteredItems = computed(() => {
    const fns = Object.values(filters.value)
    if (fns.length === 0) return items.value
    return items.value.filter(item => fns.every(fn => fn(item)))
  })

  const activeFilterCount = computed(() => Object.keys(filters.value).length)

  return {
    setFilter,
    clearFilters,
    filteredItems,
    activeFilterCount,
  }
}
```

### 5.3 Dex.vue 改造核心逻辑（示意）

```typescript
// 改造后的 Dex.vue

const searchParams = ref({
  category: undefined as string | undefined,
  status: undefined as string | undefined,
  search: '' as string,
  skip: 0,
  limit: 12,

  [() => searchParams.value.category, () => searchParams.value.status, () => searchParams.value.search],
  () => {
    searchParams.value.skip = 0
    fetchDexs()
  }

  searchParams.value.skip += 12
  fetchDexs(true) // append mode
}

// 全部走服务端
const fetchDexs = async (append = false) => {
  const { category, status, search, skip, limit } = searchParams.value
  const items = await api.dexs.list({ category, status, search, skip, limit })
  if (append) {
    dexs.value.push(...items)
  } else {
    dexs.value = items
  }
}
```

### 5.4 URL 同步模式

```typescript
// 在 Dex.vue 中：

const { params } = useServerSearch(fetcher)

// 筛选条件变化时同步到 URL
watch(searchParams, (val) => {
  const query: Record<string, string> = {}
  if (val.category && val.category !== 'all') query.category = val.category
  if (val.status && val.status !== 'all') query.status = val.status
  if (val.search) query.search = val.search
  router.replace({ query })
}, { deep: true })

// 页面加载时从 URL 恢复
onMounted(() => {
  const q = route.query
  if (q.category) searchParams.value.category = q.category as string
  if (q.status) searchParams.value.status = q.status as string
  if (q.search) searchParams.value.search = q.search as string
})
```

## 七、风险与注意事项

### 7.1 Dex 改为纯服务端筛选的影响

- **正面影响：**
  - 搜索现在真的搜了全部图鉴，而不是已加载的 12 条
  - loadMore 兼容搜索状态
  - URL 可分享
- **负面影响：**
  - 每次筛选条件变化都需要网络请求（当前约 100-300ms）
  - 如果用户高频切换分类，体验不如客户端筛选流畅
- **缓解方案：**
  - 添加 150ms 防抖（Debounce），避免快速切换时频繁请求
  - 服务器响应时间 ≤ 50ms（简单 SQL 查询应该很快）
  - 如果以后数据量很大，可以在 Store 里做简单的请求缓存

### 7.2 迁移过程中不要破坏现有功能

- 每个阶段的 PR 独立可运行
- 先加 composable（纯新建文件）→ 再改视图
- 大改 Dex.vue 时，先写好测试用例或手动验证清单

### 7.3 不要过度设计

- composeable 的 API 设计尽量简单
- 不在 composable 里搞通用 ORM 级别的抽象
- 等到三个组件都用到 2 次以上再考虑通用度
- 当前的 useClientFilter 可能只被 Archives 使用，那 API 就为 Archives 设计

## 八、总结：一句话方案

> **Archives 保持客户端筛选（提取 composable），Dex 和 PostSearch 改为纯服务端筛选（补全 API + URL 同步），统一通过 composables 层管理。**

| 视图 | 当前 | 改造后 | 改造量 |
|------|------|--------|--------|
| Archives | 纯客户端，硬编码在组件内 | 客户端，逻辑提为 composable | 小 |
| Dex | 服务端（分类/状态）+ 客户端（搜索）混用 | 纯服务端，URL 同步 | 中 |
| PostSearch | 服务端，keyword 断线，无 UI 搜索入口 | 纯服务端，补全功能 | 中 |
| 基础设施 | 无 composables 目录 | composables/ 含 4+ 工具 | 新建 |
| 后端 API | posts.list 无 search 参数；dexs.list 无 search 参数 | 各加 search 参数 | 小 |

*该文档只进行架构分析与方案设计，不涉及本地代码修改。*
