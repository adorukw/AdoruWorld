# 前端 vs 后端：功能划分决策指南

> 适用于 AdoruWorld 博客项目的架构设计参考

---

## 核心原则：网络成本 × 计算成本 × 数据体积

```
决策因子 = 数据体积 x 交互频率 x 计算复杂度 x 数据敏感性
                   ↓
       前端阈值 ← 平衡点 → 后端阈值
```

### 需要问自己的三个问题

| 问题 | 前端倾向 | 后端倾向 |
|------|----------|----------|
| **数据体积有多大？** | 小（< 500 KB） | 大（> 1 MB）或包含全文 |
| **用户交互频率？** | 高频切换（毫秒级响应） | 低频跳转（可接受 loading） |
| **逻辑复杂性？** | 简单过滤/排序/分组 | 跨表关联/聚合/权限检查 |

---

## 一、各部分功能的最佳归宿

### 🏠 前端实现（浏览器/客户端侧）

#### 1. 列表/归档/搜索的**客户端筛选与排序**

| 场景 | 说明 | 示例 |
|------|------|------|
| 分类/标签/年份过滤器 | 数据总量不大时，一次加载后用 `computed` 筛选 | 归档页按年/月/分类/标签筛选 |
| 排序切换 | 按时间、阅读量、标题排序 | 文章列表升序/降序 |
| 搜索过滤 | 标题/描述的模糊匹配（非全文搜索） | 在已加载数据中搜索关键词 |

**条件：** 数据轻量（无 content）+ 总量可接受（≤ 几百条）

**优点：** 即时响应、无网络延迟、不增加后端压力、离线可用
**缺点：** 数据量大时浏览器卡顿、首次加载仍要等待

#### 2. UI 状态与交互逻辑

| 场景 | 说明 |
|------|------|
| 折叠/展开 | 年份折叠、侧边栏收放 |
| Tab 切换 | 页面内的视图模式切换 |
| 动画/过渡 | 列表入场动画、加载骨架屏 |
| 表单校验 | 输入格式验证、必填检查 |
| 本地存储 | 主题偏好、阅读进度、草稿暂存 |

**原则：** 一切纯 UI 的、非持久化的、只影响「当前用户看到什么」的逻辑都在前端。

#### 3. 缓存与冗余数据

- 已加载的帖子列表，返回上一页时不需要重新请求
- 归档数据 `pinia store` 全局缓存，切换页面不丢失
- 触发式刷新（用户编辑文章后手动/自动刷新缓存）

### 🖥️ 后端实现（服务器侧）

#### 1. 数据写入与持久化

| 场景 | 说明 |
|------|------|
| 创建/更新/删除文章 | 必须经后端校验并写入数据库 |
| 评论提交 | 权限校验、反垃圾 |
| 用户注册/登录 | 密码加密、Token 签发 |
| 文件上传 | 存储到 OSS/本地、生成缩略图 |

**铁律：** 任何需要写入数据库的操作，必须在后端完成。前端永远不要直接操作数据库。

#### 2. 大数据量与性能敏感场景

| 场景 | 说明 | 原因 |
|------|------|------|
| 文章全文搜索 | 关键词搜索所有文章的 content | content 是大字段，不能全量加载到前端搜索 |
| 复杂聚合计算 | 总字数、总浏览量、站点头像 | 后端 SQL `SUM() / COUNT()` 更高效 |
| 大列表分页 | 文章列表（limit+offset） | 避免一次加载上千条数据 |
| 全文 content | 文章详情页只加载一篇 | 避免主页/列表页携带大字段 |

**原则：** 会返回「大部分数据用不上」的场景，后端做裁剪。

#### 3. 安全与权限

| 场景 | 说明 |
|------|------|
| 草稿/未发布的文章 | 只有作者可见，后端必须做权限校验 |
| 敏感数据 | 用户邮箱、Token、私密信息 |
| 请求频率控制 | 防止爬虫/刷接口 |

**铁律：** 前端永远不可信。权限检查必须在后端。

#### 4. 跨表关联与去重

| 场景 | 说明 |
|------|------|
| 关联文章推荐 | 基于标签匹配的后端 JOIN + GROUP BY |
| 统计汇总 | 各分类文章数、每月发文趋势 |
| 标签/分类列表 | 只返回用到的、不返回空分类 |

## 二、决策流程图

```
┌─────────────────────────────┐
│  这个功能需要做什么？          │
└─────────────┬───────────────┘
              │
      ┌───────┴───────┐
      ▼               ▼
  写数据?            读数据?
      │               │
  必须后端      ┌──────┴──────┐
      │        ▼            ▼
      │    需要权限?      纯展示?
      │        │            │
      │     必须后端   ┌────┴────┐
      │               │         │
      │           数据量大?  数据量小?
      │               │         │
      │         ┌─────┴─┐    前端
      │         │       │
      │      大字段    几百条内
      │      (content)? 的小数组
      │         │       │
      │      后端       ┌┴──────┐
      │        │       │       │
      │        │    交互频率 交互频率
      │        │    高(筛选)? 低(跳转)?
      │        │       │       │
      │        │     前端    任意
      │        │       │       │
      ▼        ▼       ▼       ▼
   后端     后端     前端     前端/后端
   (写)    (大/安全) (即时筛选) (看情况)
```

## 三、AdoruWorld 项目具体场景分析

### ✅ 当前方案（前端筛）合理的

| 场景 | 理由 |
|------|------|
| 归档页年份/月份/分类/标签筛选 | 归档数据已去掉 content，总量可控，筛选即时响应 |
| 首页文章列表排序 | 已加载 20 条，排序前端瞬间完成 |
| 标签/分类列表展示 | 后端一次返回，前端渲染即可 |
| 主题切换、暗色模式 | 纯 UI 状态，localStorage 保存 |

### 🔄 可以考虑优化的

| 场景 | 建议 |
|------|------|
| 文章列表搜索 | 目前是调后端 `?tag=&category=` 参数 → **合理** |
| 全文搜索 | 如果以后做，推荐后端 `WHERE content LIKE` 或 ElasticSearch |
| 归档筛选 | 目前前端 → **合理**，但如果文章 > 500 篇且筛选条件组合很多，可以改为 `GET /posts/archives?year=2025&category=dev&tag=vue` |

### ❌ 绝对不要放前端做的

| 场景 | 理由 |
|------|------|
| 文章 content 在列表页返回 | 大字段，网络浪费 × 性能差 × 暴露全文 |
| 未发布文章在前端可见 | 违反权限设计 |
| 直接修改数据库 | 前端不应有写数据库的权限 |
| 用户密码在前端处理 | 必须在后端哈希 |

## 四、快速判断清单

```
□ 这个是写操作吗？           → 后端 ☑️
□ 包含大字段 (content)？      → 后端裁剪 ☑️
□ 涉及权限/安全？            → 后端 ☑️
□ 数据量 > 500 条？          → 后端分页/聚合 ☑️
□ 需要数据库聚合计算？        → 后端 SQL ☑️
□ 是纯 UI 交互（折叠/动画）？  → 前端 ☑️
□ 数据已加载，只需过滤排序？   → 前端 computed ☑️
□ 需要毫秒级响应 + 高频切换？ → 前端 ☑️
□ 需要跨页面保持状态？        → 前端 store/cache ☑️

多于 4 个 ☑ 靠后端的 → 后端实现
多于 4 个 ☑ 靠前端的 → 前端实现
```

## 五、关于「前后端都做」的架构演进

一些功能不是非黑即白的，可以随着项目成长逐步迁移：

```
初期（文章 < 100 篇）
  └─ 归档筛选 → 前端一次性加载 + computed 筛选

中期（文章 100-500 篇）
  └─ 归档筛选 → 前端筛选不变，但后端新增 ?year=&category= 参数
  └─ 调用策略：首次全量加载后缓存，由后端增量更新

后期（文章 500+ 篇）
  └─ 归档筛选 → 后端负责分页 + 筛选，前端保留分组逻辑
  └─ 按需加载（先加载近一年，滚动加载更早年份）
```

**关键思路：** 不要一开始就做复杂的后端筛选。等前端真的扛不住了再迁，到时候数据结构通常是兼容的。

---

## 六、总结一句话

> **前端做「快交互」（筛选、排序、分组、缓存），后端做「重工作」（写库、大字段、聚合、安全）。两者的分界点是——数据体积 × 交互频率的交叉点。**

AdoruWorld 目前所有功能的位置都是合理的，归档页前端筛选这个决策尤其正确。继续按这个思路推进就好 😊
