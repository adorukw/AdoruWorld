## 你的前端结构 vs. 主流实践

### 你现在的结构（按「层」分）

```
src/
├── api/          ← 网络请求层
├── components/   ← 组件层
│   ├── common/   ← 通用业务组件
│   ├── layout/   ← 布局组件
│   └── ui/       ← 基础 UI 组件
├── config/       ← 配置
├── constants/    ← 常量
├── router/       ← 路由
├── store/        ← 状态管理
├── types/        ← 类型定义
├── utils/        ← 工具函数
├── views/        ← 页面
├── App.vue / main.ts / style.css
```

这种叫 **分层（Layer-based）结构**，也是 Vue 官方脚手架 Vue CLI 默认生成的模板结构。

### 对照主流项目的常见模式

| 模式 | 代表项目 | 特点 |
|------|---------|------|
| **分层（你的）** | Vue CLI 默认、Nuxt 早期 | 按技术角色分（views / store / api）|
| **功能模块（像后端建议的）** | 中型+ 项目 | 一个功能所有文件放一起 |
| **页面驱动** | Vite 官方模板 | 简单按页面分文件夹 |

## 🤔 需要改成和后端一样按模块分吗？

**不需要。** 理由有三个：

### 1. 前端的「模块」边界和后端不同

后端一个功能（post）有明确的 4 个角色（model → schema → crud → router），每个角色有自己的逻辑。而前端对一个功能做的事比较杂：

- `views/PostSearch.vue` 和 `views/PostDetail.vue` 都是文章页面，但它们共享的是 `store/post.ts` + `types/post.ts` + `api/index.ts` 中几行代码

强行合并成一个模块的话：

```
modules/post/
  ├── views/PostSearch.vue     ← 页面（看起来合理）
  ├── views/PostDetail.vue     ← 页面
  ├── store.ts                 ← 状态
  ├── types.ts                 ← 类型
  ├── api.ts                   ← API
  └── config/post-form.ts      ← 配置？
```

但 `api/index.ts` 是全局的请求封装，`store/index.ts` 统一导出了所有 store……硬拆开反而制造麻烦。

### 2. 你的项目规模不太需要

按功能模块化是**中型项目（30+ 页面）** 才会考虑的事。你现在 8 个页面，分层结构一目了然：

```
想改文章页面 → views/PostSearch.vue
想改文章状态 → store/post.ts
想改文章类型 → types/post.ts
```

不需要翻文件夹就能找到。这是小项目的自然优势。

### 3. 前端的「功能模块」通常是按领域大模块分的

真正需要模块化的时候，前端的做法是**按业务领域分大模块**，不是按「每个表一个模块」：

```
src/
├── modules/
│   ├── blog/          ← 博客模块（文章 + 分类 + 标签）
│   │   ├── pages/     ← 页面（文章列表、文章详情、归档、搜索）
│   │   ├── components/← 文章相关组件
│   │   ├── stores/    ← 文章相关状态
│   │   ├── types/     ← 文章类型
│   │   └── api.ts     ← 文章 API
│   │
│   ├── dex/           ← 图鉴模块
│   │   ├── pages/     ← 图鉴列表、详情
│   │   ├── components/← 图鉴卡片等
│   │   ├── stores/
│   │   ├── types/
│   │   └── api.ts
│   │
│   ├── media/         ← 媒体模块
│   └── admin/         ← 管理后台
│
├── shared/            ← 跨模块共享
│   ├── components/    ← 全局 UI 组件
│   ├── layouts/       ← 布局
│   └── utils/
│
├── App.vue
└── main.ts
```

但这要到项目有很多页面、多人协作的时候才有收益，你现在完全不需要。

## 🎯 可行的几个小优化（不是大改）

有几个小地方值得改，花几分钟就能提升体验：

### 1️⃣ `config/` → 合并到对应的东西里

你现在 `config/` 下 8 个文件，每个配置只在 `CrudModal.vue` 里用。可以考虑合并到 `components/common/CrudModal/` 下面。

不过目前也还行，不是什么大问题。

### 2️⃣ `types/index.ts` 统一导出

这个你已经在做了，很好。

### 3️⃣ `api/index.ts` → 可以按模块拆分

当前 `api/index.ts` 一个文件 230+ 行，所有 API 混在一起。把它拆成几个文件：

```
api/
├── index.ts          ← 只做统一导出 + request 封装
├── posts.ts          ← 文章相关 API
├── dexs.ts           ← 图鉴相关 API
├── medias.ts         ← 媒体相关 API
├── auth.ts           ← 认证相关 API（以后用）
└── system.ts         ← 系统信息 API
```

这样找 API 更快，而且跟 store 的拆分方式一致。

### 4️⃣ `App.vue` onMounted 里的数据加载

你现在的 `App.vue` 在刚启动时一口气拉 12 个 API：

```typescript
onMounted(async () => {
    await Promise.all([
        postCategoryStore.getPostCategories(),   // ✅ 首页需要
        postTagStore.getPostTags(),               // ✅ 首页需要
        postStore.getAllPosts(),                  // ✅ 首页需要
        postStore.getArchives(),                  // ❌ 只有归档页需要
        dexStore.getDexEntries(),                 // ❌ 只有图鉴页需要
        dexStore.getDexStats(),                   // ❌ 只有图鉴页需要
        dexGenreStore.getDexGenres(),             // ❌ 只有 Admin 需要
        postStore.getTotalPostsCount(),           // 👍 小数据，没事
        // ...
    ])
})
```

**建议改成按需加载**——只有首页需要的在 App.vue 加载，其他在各自页面进入时加载。这样：

- 首页打开更快
- 以后做多租户时，不同用户的页面只加载自己的数据
- 不用在 `getAllPosts` 里一次性拉上万条数据

## 📊 总结

| 事 | 结论 |
|----|------|
| 要不要像后端一样按表模块化？ | **不用**。前端和后端的分工方式不同 |
| 你现在的结构主流吗？ | **很主流**。Vue 官方模板就长这样 |
| 有没有值得做的小优化？ | **有 2 个**：拆分 api 为多文件、App.vue 按需加载 |
| 最值得做的优化是什么？ | **App.vue 按需加载**——性能提升 + 为多租户铺路 |

所以我建议，**结构不用大动**。等以后项目规模翻了倍再考虑吧～ 😊
