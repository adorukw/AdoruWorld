## 一、文章详情页：侧边栏目录实现

### 1.1 方案选择

**结论：采用纯前端自动提取目录，零后端改动。**

| 方案                         | 推荐度 | 理由                                     |
| ---------------------------- | ------ | ---------------------------------------- |
| 数据库加 toc 字段            | ❌     | 派生数据不该存两份，手动维护会同步不一致 |
| 写在内容里再分离             | ❌     | DOM 剪切脆弱，无数据绑定                 |
| **前端从 Markdown 自动提取** | ✅✅   | 零后端改动、自同步、标准做法             |

### 1.2 实现要点

**（1）给标题挂 id——修改 `marked.use` 的 heading renderer**

```typescript
const slugify = (text: string) => {
  return text
    .toLowerCase()
    .replace(/[^\w\u4e00-\u9fa5]+/g, "-")
    .replace(/^-+|-+$/g, "");
};

marked.use({
  renderer: {
    heading({ text, depth }) {
      const id = slugify(text);
      return `<h${depth} id="${id}">${text}</h${depth}>`;
    },
    // ... 保留现有的 code renderer
  },
});
```

**（2）提取目录树——从 Post.content 正则解析标题**

````typescript
interface TocItem {
  id: string;
  text: string;
  level: number;
  children: TocItem[];
}

function buildTree(items: TocItem[]): TocItem[] {
  const root: TocItem[] = [];
  const stack: { level: number; list: TocItem[] }[] = [
    { level: 0, list: root },
  ];
  for (const item of items) {
    while (stack.length > 0 && stack[stack.length - 1].level >= item.level) {
      stack.pop();
    }
    const parent = stack[stack.length - 1];
    const newNode: TocItem = { ...item, children: [] };
    parent.list.push(newNode);
    stack.push({ level: item.level, list: newNode.children });
  }
  return root;
}

const tocItems = computed<TocItem[]>(() => {
  if (!post.value) return [];
  const rawContent = post.value.content.replace(/\\n/g, "\n");
  const lines = rawContent.split("\n");
  const items: TocItem[] = [];
  const headingRegex = /^(#{1,6})\s+(.+)$/;
  let insideCodeBlock = false;
  for (const line of lines) {
    if (line.trimStart().startsWith("```")) {
      insideCodeBlock = !insideCodeBlock;
      continue;
    }
    if (insideCodeBlock) continue;
    const match = line.match(headingRegex);
    if (match) {
      items.push({
        id: slugify(match[2]),
        text: match[2].trim(),
        level: match[1].length,
        children: [],
      });
    }
  }
  return buildTree(items);
});
````

**（3）侧边栏组件——递归渲染 TocTree**

新建 `src/components/ui/TocTree.vue`：

### 1.3 常见问题与解决

#### 问题 A：侧边栏被挤到文章底部

**原因：** `<aside>` 放在了 `flex-1` 的 div 内部，不是 `flex` 容器的直接子元素，导致 flex 布局不认它是并排项目，而是左列末尾的普通块元素。

**正确结构：**

```html
<div class="flex gap-8">
  <!-- 左列：正文 -->
  <div class="flex-1 min-w-0">
    <div class="bg-white border-4...">...文章内容...</div>
  </div>

  <!-- 右列：侧边栏（和左列平级，都是 flex 的孩子） -->
  <aside class="hidden lg:block w-72 shrink-0">
    <div class="sticky top-32 bg-white border-4...">
      <h3>📑 目录</h3>
      <nav><TocTree :items="tocItems" /></nav>
    </div>
  </aside>
</div>
```

#### 问题 B：跳转标题被 sticky 进度条挡住

**原因：** Header（`sticky top-0` ~ 76px）+ 阅读进度条（`sticky top-20` ~ 80px~120px）共占据视口顶部 ~130px。`scrollIntoView` 把标题滚动到视口最顶端，正好被 sticky 元素盖住。

**解决方案：**

**方案 1（推荐，CSS 方案，通用性最强）：**

```css
.article-content :deep(h1),
.article-content :deep(h2),
.article-content :deep(h3),
.article-content :deep(h4) {
  scroll-margin-top: 130px;
}
```

`scroll-margin-top` 是浏览器原生支持的锚点偏移属性，同时修复了 URL hash 锚点和 JS scrollIntoView 的遮挡问题。

**方案 2（JS 方案，TocTree 的 handleClick）：**

```typescript
function handleClick(e: MouseEvent, id: string) {
  e.preventDefault();
  const el = document.getElementById(id);
  if (el) {
    const offset = 130; // Header + 进度条总高
    const top = el.getBoundingClientRect().top + window.scrollY - offset;
    window.scrollTo({ top, behavior: "smooth" });
  }
}
```

## 二、数据库模型分析

### 2.1 现有模型总览

| 模块         | 表名            | 核心字段                                                                                                                             | 关联                     |
| ------------ | --------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------ |
| Post         | posts           | content(Text), title, slug, description, cover_image, reading_time, word_count, views, featured, category_id, created_at, updated_at | category(N:1), tags(M:N) |
| PostCategory | post_categories | name, slug, description, icon, color                                                                                                 | posts(1:N)               |
| PostTag      | post_tags       | name, slug, color                                                                                                                    | posts(M:N)               |

| DexGenre     | dex_genres      | name, slug, color                                                                                                                    | dexs(M:N)                |
| Media        | media           | title, slug, file_path, file_size, media_type(enum), mime_type, extension, meta_data(JSON), uploaded_at                              | tags(M:N)                |
| MediaTag     | media_tags      | name, slug, color                                                                                                                    | medias(M:N)              |

### 2.2 当前评分

| 维度     | 评分       | 说明                                                     |
| -------- | ---------- | -------------------------------------------------------- |
| 模块划分 | ⭐⭐⭐⭐⭐ | Post / Dex / Media 边界清晰，module 结构统一             |
| 关联关系 | ⭐⭐⭐⭐   | 多对多关联表标准，selectinload 合理                      |
| 字段设计 | ⭐⭐⭐     | 有小毛病但整体能用                                       |
| 可迁移性 | ⭐⭐       | 没有数据库迁移系统，是最大短板                           |
| 扩展预留 | ⭐⭐⭐     | Media 的 meta_data JSON 是亮点，Post 和 Dex 缺少类似设计 |

### 2.3 发现的问题

#### 🔴 最高风险：没有数据库迁移系统

```python
# database.py
async def init_db():
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
```

`create_all` 只建新表，不修改已有表。加字段、改类型时只能删库重建，**上线后不可行**。

**解决方案：引入 Alembic**

```
pip install alembic
alembic init alembic
# 配置 alembic/env.py 连接 DATABASE_URL
alembic revision --autogenerate -m "init"
alembic upgrade head
```

之后每次改 model → `alembic revision --autogenerate -m "xxx"` → `alembic upgrade head`。

#### 🟠 中风险：字段定义问题

**① DexGenre.color nullable 冲突**

```python
# dex_genre/model.py: 第 20 行
color: Mapped[str | None] = mapped_column(String, nullable=False)
#               ↑ Optional                    ↑ NOT NULL —— 冲突
```

改为统一：要么 `nullable=True`，要么去掉 `| None`。

**② PostTag.slug 可空 vs PostCategory.slug 不可空**

```python
# post_tag/model.py: 第 17 行
slug: Mapped[str | None] = mapped_column(String, nullable=True)
# post_category/model.py: 第 15 行
slug: Mapped[str] = mapped_column(String, nullable=False, unique=True)
```

一样的标签体系，约束不一致。建议统一为不可空。

**③ Post.cover_image 可空 vs Dex.cover_image 不可空**

```python
# post/model.py: 第 28 行
cover_image: Mapped[str | None] = mapped_column(String, nullable=True)
# dex/model.py: 第 30 行
cover_image: Mapped[str] = mapped_column(String, nullable=False)
```

Dex 没封面图就报错。建议统一为可空，或前端表单都做必填校验。

**④ PostCategory.description 使用 String 而非 Text**

```python
description: Mapped[str] = mapped_column(String, nullable=True)
```

SQLite 中 String 默认 VARCHAR，长描述可能被截断。Post 和 Media 同类字段用的 Text，不一致。建议改为 Text。

#### 🟡 低风险

**⑤ Dex 缺少时间戳**

```python
# dex/model.py 缺少：
# created_at: Mapped[datetime]
# updated_at: Mapped[datetime]
```

Post 有，同为内容实体的 Dex 却没有。建议加。

**⑥ Dex.start_date / finish_date 是字符串**

```python
start_date: Mapped[str | None] = mapped_column(String, nullable=True)
finish_date: Mapped[str | None] = mapped_column(String, nullable=True)
```

存 `"2026-01"` 没问题，但如果有按时间范围筛选需求（统计图表等），字符串效率低且格式难统一。如有查询需求，改为 Date 类型。

**⑦ Post 和 Dex 缺少 JSON 扩展字段**

Media 有 `meta_data: dict = mapped_column(JSON, default=dict)`，可以自由加元信息而不改表。Post 和 Dex 建议加同样的字段，为未来扩展预留。

**⑧ 所有删除都是 hard delete**

没有回收站/软删除能力。如果未来有回收站需求，可加 `deleted_at: datetime | None` 做软删除。当前不紧急。

### 2.4 修复优先级

| 优先级 | 事项                               | 工作量        | 收益                        |
| ------ | ---------------------------------- | ------------- | --------------------------- |
| **P0** | 上 Alembic 迁移系统                | 半天          | 不改表就崩，必做            |
| **P1** | 修 DexGenre.color nullable 冲突    | 改 1 行       | 防止运行时错误              |
| **P1** | 统一下 PostTag.slug 的 nullable    | 改 1 行       | 前端用 slug 查询时不出 BUG  |
| **P2** | Post 和 Dex 加 meta_data JSON 字段 | 改 2 个 model | 一劳永逸，以后加字段不改表  |
| **P2** | Dex 加 created_at / updated_at     | 改 1 个 model | 让 Dex 有基本的时间追溯能力 |
| **P3** | PostCategory.description 改 Text   | 改 1 个 model | 防止长描述被截断            |

## 三、RAG 知识库扩展规划

### 3.1 核心思路

RAG（检索增强生成）的核心流程：

```
文章原文（Post.content）→ 切块 → 向量化 → 存储 → 检索 → 增强生成
```

项目 README 中已写明目标：「接入大模型构建成个人知识库」。

当前优势：Post.content 已是干净的 Markdown 纯文本，直接就是 RAG 的原材料。

### 3.2 ContentChunk 表：内容块

**ContentChunk 和 Post.content 的关系：**

```
Post.content = 一整块牛排（原文）
ContentChunk = 切好的牛排块（索引），每块标着来源
```

两者不是替代关系，是「原文」和「索引」的关系。原文永远不变，chunks 供检索用。

**表结构定义：**

```python
class ContentChunk(Base):
    __tablename__ = "content_chunks"

    id: str = mapped_column(String, primary_key=True, default=_uuid)
    entity_type: str   # "post" | "dex" | 未来其他实体类型
    entity_id: str     # 对应实体的 ID
    chunk_index: int   # 块序号，用于排序和追溯
    content: str       # 切好的文本片段
    heading: str | None  # 来源标题/章节名（如果是文章的话）
    token_count: int   # token 数，方便管理 context window
    # 后续可加：
    # embedding BLOB / embedding_id  ← 向量
    # created_at
```

### 3.3 切块策略

以一篇 Markdown 文章为例：

```markdown
# 介绍

这是关于 EVA 的背景介绍。

## 登场人物

### 碇真嗣

真嗣是 14 岁的少年。

### 绫波丽

丽是神秘的少女。
```

切块结果：

| entity_type | entity_id | chunk_index | heading             | content                     | token_count |
| ----------- | --------- | ----------- | ------------------- | --------------------------- | ----------- |
| post        | xxx       | 0           | "介绍"              | "这是关于 EVA 的背景介绍。" | 25          |
| post        | xxx       | 1           | "登场人物 / 碇真嗣" | "真嗣是 14 岁的少年。"      | 14          |
| post        | xxx       | 2           | "登场人物 / 绫波丽" | "丽是神秘的少女。"          | 15          |

常用切块策略：

- **按标题切**：每个 h2/h3 一个块（最适合 Markdown 结构）
- **按 token 数切**：超过阈值（如 500 token）断开
- **混合**：先按标题切，超过阈值则子节再细分

### 3.4 切块触发时机

| 时机                    | 方式                                          |
| ----------------------- | --------------------------------------------- |
| 保存/更新文章时自动触发 | 在 CRUD 的 save 逻辑末尾加一段切块代码        |
| 每天凌晨定时全量重建    | cron + 后台脚本                               |
| 手动触发                | 新增 API `/reindex/{entity_type}/{entity_id}` |

**每次保存时全量覆盖旧 chunks，而不是增量更新。** 确保 chunks 永远和当前 content 一致。

```python
async def reindex_post(db, post_id: str):
    post = await get_post(db, post_id)
    # 删除旧 chunks
    await db.execute(
        delete(ContentChunk).where(
            ContentChunk.entity_type == "post",
            ContentChunk.entity_id == post_id
        )
    )
    # 切块并写入新 chunks
    chunks = chunk_markdown(post.content)
    for i, chunk in enumerate(chunks):
        db.add(ContentChunk(
            entity_type="post",
            entity_id=post_id,
            chunk_index=i,
            content=chunk.content,
            heading=chunk.heading,
            token_count=count_tokens(chunk.content),
        ))
    await db.commit()
```

### 3.5 RAG 检索流程

```
用户提问: "EVA 的碇真嗣是什么性格？"

1. 把问题转成向量（通过 embedding API）
2. 在向量库中搜索最相似的 5 个 ContentChunk
3. 找到匹配的 chunk 行
4. 查回 entity_type + entity_id → 找到原文 Post
5. 把 chunk.content + Post 元数据发给 LLM
6. LLM 根据检索到的内容回答
7. 回答附带来源: "来自文章《EVA 深度解析》- 登场人物/碇真嗣"
```

## 四、知识图谱扩展规划

### 4.1 实体关系表 EntityRelation

```python
class EntityRelation(Base):
    __tablename__ = "entity_relations"

    id: str = mapped_column(String, primary_key=True, default=_uuid)
    source_type: str     # "post" | "dex" | 其他实体类型
    source_id: str       # 来源实体的 ID
    target_type: str     # "post" | "dex" | "media" | "tag" | ...
    target_id: str       # 目标实体的 ID
    relation_type: str   # "mentions" | "references" | "related_to" | "series_of"
    weight: float        # 关系强度，默认 1.0（可用作系列序号等）
    created_at: datetime
```

### 4.2 关系类型定义

| 关系类型   | 含义                | 示例                                |
| ---------- | ------------------- | ----------------------------------- |
| mentions   | A 提到了 B          | Post → Dex（文章里说了某个作品）    |
| references | A 引用了 B          | Post → Post（文章引用了另一篇文章） |
| related_to | A 和 B 相似         | Dex → Dex（相似作品关联）           |
| series_of  | A 是 B 系列的一部分 | Post → 系列标识（文章属于某个连载） |

### 4.3 关系的填充方式

有三种方式，从简单到复杂：

#### 方式一（推荐先做）：从文章内容自动匹配

**核心思路：不要人工从几百个图鉴里「选」，改成在文章内容里「写」，系统自动识别。**

用户在 content 里写：

```markdown
昨天又看了一遍「EVA」，发现了一些新的细节。
和「攻壳机动队」不同，EVA 更注重心理描写。
```

保存时后台自动处理：

1. 从 content 里提取 `「」`、`""`、`《》` 等引号内的文本
2. 去 Dex 表匹配 `title` / `original_title`
3. 匹配成功 → 写入 EntityRelation

**匹配词典来源：** Dex 表里的 `title` + `original_title` 本身就是最好的关键词库。可以再加「别名」字段进一步提高匹配率。

**前端预览增强：** 匹配到的关键词可在编辑器中加虚线下划线，hover 显示「点击关联到图鉴 EVA」。

**兜底：** 页面底部展示「系统自动识别到以下关联」，让用户勾选确认或手动补充。

```
需要手动从几百个图鉴里挑？→ 不需要。用户已经写了，系统在找。
```

#### 方式二（进阶）：LLM 自动抽取

文章保存后，把 content 发给 LLM：

```
Prompt: 从以下文章中提取所有提到的作品名称，匹配到我的图鉴库中。
```

LLM 返回匹配结果，自动填充 EntityRelation。

#### 方式三（轻量补充）：规则匹配

正则匹配 Dex 表的所有 title / original_title，在 content 中搜索是否存在。存在即匹配。

### 4.4 关于「文章提到的作品」交互设计

**不在写文章时建关系——在保存文章时自动建。**

用户只需要正常写文章，提到作品名时用书名号或引号包起来即可。

系统自动提取并匹配，匹配结果展示在编辑页面底部的确认区。

### 4.5 关于「关系会过时」的问题

**每次保存时全量覆盖，不做增量更新。**

```python
async def save_post_with_relations(db, post_id, content, ...):
    # 1. 保存文章
    post = await update_post(db, post_id, content, ...)

    # 2. 删除这篇文章旧的 mentions 关系
    await db.execute(
        delete(EntityRelation).where(
            EntityRelation.source_type == "post",
            EntityRelation.source_id == post.id,
            EntityRelation.relation_type == "mentions"
        )
    )

    # 3. 从当前 content 重新提取并匹配
    mentioned_ids = extract_and_match(content)
    for target_id in mentioned_ids:
        db.add(EntityRelation(
            source_type="post", source_id=post.id,
            target_type="dex", target_id=target_id,
            relation_type="mentions"
        ))

    await db.commit()
```

- 用户删了一段话 → 提到的作品消失 → 下次保存匹配不到 → 关系自动删除
- 用户加了新内容 → 匹配到新作品 → 关系自动增加
- 永远和 content 实际情况一致

## 五、系列（Series）与分类（Category）

### 5.1 区别详解

| 维度             | Category（分类）               | Series（系列）                                                   |
| ---------------- | ------------------------------ | ---------------------------------------------------------------- |
| 一篇文章能有几个 | 1 个                           | 0 或 1 个                                                        |
| 作用             | 告诉读者「这是什么类型的内容」 | 告诉读者「这是哪个连载的第几篇」                                 |
| 是否可排序       | 不分先后                       | 有序号：第 1 篇、第 2 篇……                                       |
| 和文章内容的关系 | 分类是「属性」                 | 系列是「结构」                                                   |
| 前端展示方式     | 标签徽章                       | 文章开头显示「系列·第 N 篇」<br>末尾显示「← 上一篇 \| 下一篇 →」 |

**示例：**

```
分类（category）：  漫评 | 技术 | 日记 | 游记
                  ↑ 文章「属于」哪个大类

系列（series）：    《EVA 深度解析系列》
                    ├── 第1篇：EVA 的背景介绍
                    ├── 第2篇：EVA 的角色分析
                    └── 第3篇：EVA 的宗教隐喻
                  ↑ 文章是某个连载的一部分
```

**核心区别：** Category 和 Series 是正交的两个维度。同一分类下的文章可以属于不同系列，同一系列的文章可以跨分类（虽然少见）。

### 5.2 Series 表结构（未来扩展）

```python
class Series(Base):
    __tablename__ = "series"

    id: str = mapped_column(String, primary_key=True, default=_uuid)
    name: str                    # "EVA 深度解析系列"
    description: str | None
    cover_image: str | None

# Post 表增加字段
# series_id: str | None = mapped_column(String, ForeignKey("series.id"), nullable=True)
# series_order: int | None    # 系列内序号
```

也可以用 EntityRelation 表达系列关系而不建 Series 表（用 `series_of` 关系类型 + `weight` 当序号），但系列是一种**结构关系**，单独建表更清晰。

### 5.3 现在要不要建？

**不要。** 原因是：

- 现在没有连载内容，建一张空表没有意义
- 等真要写系列文章时，用 Alembic migration 加 `series` 表和 `Post.series_id` 字段，一天搞定
- 当前的 category 已经能满足「漫评」「技术」等粗粒度分类需求
